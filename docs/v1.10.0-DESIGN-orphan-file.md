# v1.10.0 设计稿 1：孤儿文件修复（临时目录 + finally 清理）

> 状态：待评审。批准后实施，单 commit，可独立 revert。
> 背景：见 docs/v1.9.2-OPTIMIZATION-PLAN.md 附录 C。

## 问题回顾

`hooks.ts` 非 inPlace 流程现状：

```
IOUtils.write(outputPath, outputPdf)      ← 把 -ocr.pdf 写在源文件旁边（或源附件 storage 目录内）
createOCRAttachment(...)                   ← importFromFile 是拷贝语义
```

- 成功：拷贝进新附件的 storage 后，源位置的 `-ocr.pdf` **永久遗留**（链接附件场景遗留物在用户自己的文件夹里，可见）；
- 用户在"创建父条目"弹窗点取消：写盘的文件成为**完全孤儿**（无任何附件引用）。

## 方案（已选 a：临时目录 + finally）

写入位置改为 Zotero 临时目录，导入（拷贝）完成后无论成败一律删除：

```ts
// hooks.ts execute() 非 inPlace 分支
const tmpDir = Zotero.getTempDirectory().path;
const outputPath = PathUtils.join(tmpDir, `pdfocr-${Date.now()}-${index}.pdf`);
await IOUtils.write(outputPath, outputPdf);
try {
  const attachResult = await createOCRAttachment({ path: outputPath, ... });
  if (attachResult.status === "standalone_attachment") { ...确认父条目... }
  ...
} finally {
  try { await IOUtils.remove(outputPath, { ignoreAbsent: true }); }
  catch (err) { log(`temp cleanup failed: ${err}`); }
}
```

要点：

1. **finally 保证三态清理**：成功、创建附件抛错、用户取消父条目确认——临时文件都删除。
2. **inPlace 路径不变**：仍直写真实 [OCR] 附件文件（写前关阅读器 + 重试写已有逻辑）。
3. **`[OCR]` 命名不受影响**：附件标题由 `createOCRAttachment` 的 title 参数决定，与文件名无关。
4. **覆盖守卫属性由结构保证**：临时路径与源路径永不可能相同，原 `deriveOcrOutputPath` 的防覆盖职责自然消失。

## 变更清单

| 文件 | 动作 |
|------|------|
| `addon/bootstrap.js` | `addonContext.PathUtils = PathUtils;`（IOUtils 同级的 Gecko 全局，join 处理跨平台分隔符） |
| `src/hooks.ts` | 非 inPlace 分支：temp 路径 + finally 清理；`deriveOcrOutputPath` 调用点移除 |
| `src/zotero/attachment-service.ts` | 删除 `deriveOcrOutputPath`（无调用点后删除，不留死代码） |
| `tests/unit/attachment-service.test.ts` | 删除对应的 3 个规格测试 |

## 决策点（请确认）

- **删除 `deriveOcrOutputPath`**：1.9.2 刚建的函数+测试，本方案下防覆盖属性由"写临时目录"结构性保证，函数失去调用点。建议删除（不留死代码）；若你想留作公共工具函数，我可以改为保留并标注"工具函数"。

## 边界与风险

- `Zotero.getTempDirectory()` 在 Zotero 7 返回 nsIFile，`.path` 取字符串；bootstrap 已暴露 Zotero 全局，沙箱可调。
- 临时文件生命周期极短（写盘 → 导入拷贝 → 删除，秒级），不涉及时序竞争。
- 附件导入失败的错误路径不变：执行器 catch 已有 finishTask(failed) 展示。
