### 1.1 预处理参照实现测试 `tests/unit/preprocess.test.ts`（新）

把 `src/ocr/preprocess.ts` 里**当前的算法逐字拷贝**进测试文件，作为参照实现（reference）。对三组固定输入，断言「被测实现 === 参照实现」逐位相等（Float32Array 逐元素 `===`）：

| 用例 | 输入 | 覆盖路径 |
|------|------|----------|
| det 缩放 | 100×60 渐变 RGBA（像素值 = 索引的确定性函数），`limitSideLen=64` | 强制缩小 + roundTo32 宽高非对称 |

## Phase 2 — 三处正确性修复（每处一个 commit）

### 2.1 输出路径守卫

**改什么**
- `src/zotero/attachment-service.ts` 末尾新增 pure 函数：

```ts
/** 推导 [OCR] 输出路径；路径不含 .pdf 后缀时追加后缀，绝不返回与输入相同的路径。 */
export function deriveOcrOutputPath(path: string): string {
  const replaced = path.replace(/\.pdf$/i, "-ocr.pdf");
  return replaced !== path ? replaced : `${path}-ocr.pdf`;
}
```

- `src/hooks.ts:215` 改为：

```ts
const outputPath = deriveOcrOutputPath(job.path);
if (outputPath.toLowerCase() === job.path.toLowerCase()) {
  throw new Error(`无法为 ${job.path} 推导安全的 OCR 输出路径，已中止（不会覆盖源文件）`);
}
```

**为什么（大白话）**：现在的代码是「把文件名里的 .pdf 换成 -ocr.pdf」——可万一某个 PDF 附件的文件名根本没有 .pdf 后缀（链接附件、奇怪命名的文件都可能），这行替换什么都没干，接下来写盘的那行就把**你的原文件直接覆盖掉了**，OCR 管线一旦中途出错，原文档就毁了。修完之后：能换名的换名，不能换名的加后缀，加完还不行的直接报错拒绝干活——宁可不做，绝不覆盖原件。

**完成标志**：1.2 的测试全绿；用无扩展名附件实测右键 OCR，源文件 sha256 不变。

```ts
    catch { return undefined; }

  return parseOcrPrefs({

    detThresh: get("detThresh"),
    detBoxThresh: get("detBoxThresh"),
    detMaxRotDeg: get("detMaxRotDeg"),
    cropMode: get("cropMode"),
    ocrWorkers: get("ocrWorkers"),
    autoOpenAfterSuccess: get("autoOpenAfterSuccess"),
  });
}
```

```js
function readThresholdInt(key, fallbackPercent) {
  var v = Number(readPref(key));
  if (isNaN(v)) return fallbackPercent;
  if (v > 0 && v < 1) return Math.round(v * 100);  // legacy 浮点
```

## Phase 3 — 两处性能改动（Phase 1 的测试在这里兜底）

### 3.1 预处理融合

**改什么**：`src/ocr/preprocess.ts` 内部重写，导出签名与返回结构全部不变。

现状是三个 pass：`resizeBilinear` 产出 HWC 布局的 RGB 浮点数组 → 单独一遍循环归一化 → 再一遍 HWC→CHW 转置。1536×1536 规模下每页约 700 万次冗余内层运算 + 一份中间数组。

融合成单 pass `resizeToCHW`：采样 → 归一化 → 直写目标布局。关键约束：**插值算术逐字保留**——

```
top = p00 + (p10 - p00) * xFrac
bot = p01 + (p11 - p01) * xFrac     ← 注意是 xFrac，不是 yFrac
out = top + (bot - top) * yFrac
norm = (out / 255 - 0.5) / 0.5      ← 与旧代码相同的运算顺序
```

det 路径 RGB 直写 `chw[c*plane + dy*dstW + dx]`；rec 路径把 c 的写入顺序换成 BGR（R 写 plane 2、B 写 plane 0），交换只是路由、没有算术变化。`detPreprocess` / `recPreprocess` 对外行为不变（`scaleX/scaleY` 等字段原样返回）。

**为什么（大白话）**：原来一张页面图像进流水线要被完整过三遍（缩放一遍、归一化一遍、重排一遍），现在一遍干完三件事，还省掉一份 700 万个浮点数的中间数组。识别模型吃的输入必须一个比特都不变——所以 Phase 1 的参照测试在这里兜底。

**完成标志**：1.1 三组用例逐位 `===` 全绿；单页 OCR 手测不劣化（预期 det 预处理段 -20~30%，整体感知不大）。

### 3.2 模型单次 fetch 分发

**改什么**：`src/ocr/ocr-engine.ts:85-93`。现状每个 worker 各调一次 `fetchModelAssets()`——8 核时重复读 det(4.7MB)+rec(10.9MB)+wasm(~13MB) 共 8 遍。改为：

```ts
const assets = await fetchModelAssets(); // 一次，母本留在本函数作用域
await Promise.all(Array.from({ length: n }, async () => {
  if (this.cancelled()) throw new Error("OCR cancelled");
  const client = WorkerClient.open(workerUrl);
  this.clients.push(client);
  // init 会 transfer（detach buffer）——每个 worker 必须拿独立副本
  await client.init({
    wasm: assets.wasm.slice(0),
    det: assets.det.slice(0),
    rec: assets.rec.slice(0),
    dict: assets.dict,   // 结构化克隆本身拷贝；worker 侧还有 slice()，双重安全
  }, { detLimitSideLen, detThresh, detBoxThresh, maxRotDeg, cropMode });
  client.onError((message) => onProgress?.({ stage: "worker-error", percent: -1, message }));
}));
```

**边界决策**：`assets` 用 run() 内局部变量，**不做跨任务缓存**——engine 每任务新建，模块级缓存会让 28MB 常驻内存。跨任务复用留给 v1.10 与常驻 worker 池一起决策。收益是「每任务 n 次 IO → 1 次」，模型编译本来就在各 worker 并行，不受影响。

**为什么（大白话）**：8 个工人开工，原来是每人自己跑去仓库搬一套 28MB 的工具箱（搬 8 次），现在是仓库搬一套出来，复印 8 份发下去。工人手里的工具还是各一套（沙箱限制，没法共用），只是路上少跑 7 趟。

**完成标志**：`npm test` 全绿（现有 ocr-engine 测试 mock 过 fetch）；手测 4 核 / 8 核启动到首帧的耗时对比 1.9.1 不劣化；Phase 0 基线 PDF 的输出文本层与 1.9.1 一致。

`scripts/` 只留：`build.mjs`、`verify-xpi.mjs`、`gecko140-customElements.js`、`zotero10-menuManager.js`、`zotero10-pluginAPIBase.mjs`（后三个是 Zotero API 行为参照，有文档价值）。`.gitignore` 的 `/scripts/*.pdf` 等 6 条规则同步改为 `tools/debug/`。

**为什么（大白话）**：仓库根下躺着 20 多个一次性调试脚本和二进制 dump，新来的协作者分不清哪些是正经工具哪些是考古现场。git 历史都在，搬家不丢东西。

## 附录 C — 孤儿文件专述（v1.10，本轮只记录不修）

`hooks.ts` 非 inPlace 流程现状时序：

```
hooks.ts:216  IOUtils.write(outputPath, outputPdf)     ← 先写盘
hooks.ts:219  createOCRAttachment(...)                  ← 查父条目
  ├─ 有父条目 → importFromFile(outputPath) 拷入新附件 storage → outputPath 遗留 ❗
  └─ 无父条目 → confirmCreateParent 弹窗
       ├─ 确认   → 同上，outputPath 遗留 ❗
       └─ 取消   → outputPath 成为完全孤儿（无附件引用）❗
```

问题比「取消留孤儿」更宽：**importFromFile 是拷贝语义，无论确认还是取消，写盘的 `-ocr.pdf` 都会遗留**。v1.10 修复方向（倾向 a）：

- **a. 临时目录 + finally 清理**：outputPath 改写临时目录，importFromFile 拷贝完成后 `IOUtils.remove(outputPath, { ignoreAbsent: true })`；cancel/异常路径同样清理。改动集中在 hooks.ts 的 execute，attachment-service 不动。
- b. 确认前置：把 confirmCreateParent 提到写盘之前（需在 resolve 阶段区分 standalone），时序变复杂，且不解决成功路径遗留。
- c. 失败/取消时删除 + 成功时保留并文档化——不推荐，仍留垃圾。
